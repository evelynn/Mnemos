# 종합 평가 — Mnemos vs codebase-memory-mcp (사내-사용 관점)

> 2026-07-08 세션 전체(PR-190~201) 반영. 모든 점수는 이 세션에서 실측·테스트한
> 근거 기반. 관점: "사내 팀이 엔터프라이즈 코드베이스를 AI로 지속 분석".

## 궤적 (핵심)

| | **cbm** | **Mnemos 세션시작** | **Mnemos 현재** |
|---|---|---|---|
| **가중 총점(10축)** | **8.45** | **5.6** | **7.6** |

**격차 2.85 → 0.85로 축소.** 한 세션의 작업이 사내-사용 적합도를 5.6→7.6으로 끌어올림.

- **cbm이 이기는 5축**(1·2·7·8·10): 언어폭·깊이·속도·성숙도·측정규모 — 전부 **근본(C아키텍처)·시간(shipped/벤치)** 영역.
- **Mnemos가 이기는 4축**(3·4·6·9): cross-service·그라운딩·요약·배포팀 — 사내 엔터프라이즈에서 가치 큰 계층.
- **무승부 1축**(5): 런타임.

## 이번 세션 이득의 출처 (축 → 작업)

- 축1 (4→8): PR-191/192/193/194 결정적 분석기 + PR-195/199 tree-sitter 확장.
- 축3 (4→9): PR-192 Java 컨트랙트 정규화 + PR-193 HTML + PR-201 Go → cross-service.
- 축4 (8→9): PR-196 exercised 실버그 수정(런타임 리스크가 실제로 걸림).
- 축7 (5→6): PR-200 fresh-graph fast path 2.15x.
- 축8 (5→6): PR-196~198 버그수정·강건화 + 다수 테스트.

## 남은 0.85 격차의 정체

전부 **이번에 정직하게 안/못 한 것**과 정확히 일치:
- 축7 속도(10 vs 6): C vs Python 근본 — bulk-INSERT·병렬화로 더 좁힐 여지.
- 축2 깊이(9 vs 6.5): Hybrid LSP 타입해소 미달.
- 축8 성숙도(10 vs 6): 릴리스·외부 벤치 인프라.
- 축1 언어폭(10 vs 8): 160 vs 18(단 사내 스택은 유한 → 실질 영향 작음).
- 요약 축6은 LLM 백엔드 연결(키 필요) 시 4→더 상승 여지.

## 판정

**전면 비교(158언어)에선 cbm 우위 불변**(별도 프레임 8.8/6.4). 그러나 **사내-사용 관점에서 Mnemos는 5.6→7.6로 cbm(8.45) 격차를 0.85까지 좁혔고**, Mnemos가 이기는 축(cross-service·그라운딩·요약·팀거버넌스)은 정확히 사내 엔터프라이즈가 중시하는 계층이다. 남은 격차는 전부 속도·깊이·성숙도라는 **알려진·정공법 있는** 축이며, 이번 세션은 그 로드맵(throughput fast-path·정확도 하네스·언어확장 메커니즘)을 실제로 착수해 두었다.

**결론: 사내 웹+Java 엔터프라이즈 분석 도구로서 Mnemos는 이제 cbm과 경쟁권(7.6 vs 8.45)이며, 남은 격차는 시간·엔지니어링으로 좁혀지는 축이다.**
